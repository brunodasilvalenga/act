**012 required one revision round.** The executor correctly followed the
plan as written but flagged (rather than silently shipping or unilaterally
fixing) a real functional defect: `act env add <name> --profile P --region
R` — the exact syntax the plan's own steps, help text, and README examples
specify — always failed with "Error: at least one of --profile or --region
is required", regardless of flag position. Root cause: `main.go`'s
top-level `parseGlobalFlags` (run on full `os.Args` before subcommand
dispatch) already strips any `--profile`/`--region` token out of argv
before `runEnv`'s local `flag.NewFlagSet("env add", ...)` — which defined
its own same-named flags — ever saw them. Reviewer reproduced the bug
independently, then dispatched a revision: dropped the colliding local
`FlagSet` and had `env add` reuse the already-resolved global
`profile`/`region` values instead (passed into `runEnv` as parameters),
matching the calling convention `act --profile prod --region us-west-2 env
add prod` (global flags precede the subcommand, same as every other
subcommand in this CLI). Updated `printEnvHelp()` and `README.md`'s example
to match. Reviewer independently re-verified: `go build`/`go test ./...`
clean, and manually exercised `env add`/`env list`/`env rm` end-to-end
confirming the fix and confirming the "no profile or region given" error
path still works.

## Findings considered and rejected

- **`go.mod`'s `go 1.26.3` directive**: not a bug — Go has supported
  3-component `go` directives since 1.21; this is a normal toolchain-pin
  format, not an error. (Plan 001 does bump the version to close real CVEs,
  but the *format* itself was never the issue.)
- **Sequential AWS CLI calls in `act ecs logs` auto-detect** (cluster list →
  service list → describe-services → describe-task-definition): each call
  fetches genuinely different data needed for sequential user picks; no
  real algorithmic win is available without restructuring the interactive
  flow itself. Not worth a plan.
- **Missing CI dependency caching** (`actions/cache` in `ci.yml`/
  `release.yml`): the dependency set is tiny (~24 modules via
  bubbletea/lipgloss and transitives), so the marginal CI-speed benefit
  doesn't justify a dedicated plan. `setup-go`'s built-in default caching
  likely already covers most of this.
- **Adding GPG/Sigstore signature verification to the self-upgrade flow**:
  a materially larger change (key management, signing in the release
  pipeline) than the fail-closed checksum fix in plan 003; explicitly
  deferred as a bigger, separate initiative if the maintainer wants stronger
  supply-chain guarantees later.
- **Archive extraction path-traversal tests for `internal/updater/extract.go`**:
  genuinely valuable but requires building crafted fixture archives with
  malicious entries — a large enough sub-effort that it was excluded from
  plan 015's scope rather than bundled in; flagged as a good follow-up in
  plan 015's maintenance notes.
- **Extending the RDS-style bastion-forwarding pattern to
  ElastiCache/DocumentDB/MSK**, **`act profile list`/`act login` for SSO
  token refresh**, and **Lambda log tailing**: all three are grounded
  direction findings (see the original audit's direction section) but are
  larger, more speculative feature investments than a "fix this bug" plan —
  they were not selected for planning in this batch (only the favorites/
  environments CRUD gap, plan 012, was selected from the direction
  category). If the maintainer wants to pursue any of these, they should
  each get their own `plan <description>` or `next`-style design/spike
  plan, not be retrofitted into this batch.
